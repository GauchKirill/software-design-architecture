# ADR-0004: DI на Boost.DI

- **Статус:** принято
- **Контекст:** по ТЗ нужен DI-контейнер на краю приложения. В системе стоит Boost 1.83, но
  **Boost.DI не входит в состав Boost** (ни 1.83, ни 1.90): это отдельный проект
  [boost-ext/di](https://github.com/boost-ext/di) («not an official Boost library»).

## Решение

1. Использовать Boost.DI (boost-ext.di) v1.3.0 — официальный single header, C++14+, зависимости
   только от стандартной библиотеки.
2. Закрепить заголовок в `third_party/boost-ext/di/`:
   `include/boost/di.hpp`, SHA256 `bd74fa32901ceb090efa3eef9414425f45d0c4a4ab7ca9b573052243ab89d83a`,
   лицензия BSL-1.0 и README с источником/версией. Это даёт офлайн-воспроизводимую сборку.
3. Подключать заголовок как `SYSTEM`-include через INTERFACE-таргет `pos::boost_di`; опция
   `POS_BOOST_DI_INCLUDE_DIR` позволяет подменить его системным, если появится.
4. Собирать в `src/app/composition_root.cpp`: singleton `InMemoryDatabase`, порты → адаптеры,
   `Clock` → `SystemClock`, `FinalScorePolicy` → lambda-фабрика, собирающая Strategy + Decorator
   по `AppConfig`; сервисы и `PosFacade` — singleton. Верхний объект создаётся
   `injector.create<std::shared_ptr<PosFacade>>()`.
5. Тестировать не «контейнер вообще», а собранный граф: `tests/app/composition_root_test.cpp`
   проверяет общее состояние репозиториев (reader/writer смотрят в одну БД), выбор формулы и
   округления, отказ при неверной конфигурации.

## Обоснование

- Требование «DI на Boost.DI» выполняется без установки неофициального пакета в систему и без
  сетевой зависимости при сборке.
- Compile-time контейнер: отсутствующая зависимость или цикл обнаруживаются компилятором.
- Lambda-binding — документированный способ подставить runtime-конфигурацию (`formula`, `rounding`)
  в compile-time граф; проверено на GCC 16/C++23.

## Последствия

- Диагностика ошибок DI — шаблонная и длинная; помогает `BOOST_DI_CFG_DIAGNOSTICS_LEVEL` и
  маленький граф.
- Версию Boost.DI нужно обновлять вручную (файл + SHA256 + README).
- Boost.DI не является официальной библиотекой Boost; это явно указано в README, чтобы не
  вводить проверяющего в заблуждение.

## Альтернативы

- **Самописный контейнер** — отвергнуто: больше кода не по теме ДЗ и меньше проверенного поведения.
- **Ручная сборка графа в `main`** — отвергнуто: требование DI-контейнера и риск «wiring mess».
- **Service Locator** — отвергнуто: скрытые зависимости и тест-хостинг.
- **Установка boost-ext/di в `/usr/local`** — отвергнуто: загрязняет систему и ломает
  воспроизводимость репозитория.
